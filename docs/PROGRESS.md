## Competitor review: SpendMate

Subsequent user decision: use SpendMate's frontend as the design/reuse base for a more user-friendly Countersign interface after current setup is finished. This supersedes the earlier recommendation to preserve all existing presentation. Implementation planning must preserve Countersign's core workflows and clearly identify any additional functional scope; a redesign does not by itself implement or approve a general-purpose wallet-management agent.

Reviewed 2026-10-06 at public source commit `1fed614f9c79e1932e5e8927e3e043a15ade5170`. Sources: [ETHGlobal showcase](https://ethglobal.com/showcase/spendmate-wmewx), [repository](https://github.com/Meriem-BM/x402ops), [public demo landing](https://x402ops.vercel.app/). The landing page requires a wallet connection; no wallet was connected, no transactions were tested, and the submission's deployed behavior was not independently verified. The README's video URL is a placeholder, so no working video was reviewed.

The submission describes no-code agent creation, dedicated CDP wallets, spending-policy configuration and activity tracking. The repository includes a wallet-specific chat page, a wallet-creation route, policy cards and usage/activity components. These are useful product patterns, but implementation claims need qualification:

- The [chat hook](https://github.com/Meriem-BM/x402ops/blob/1fed614f9c79e1932e5e8927e3e043a15ade5170/hooks/useAgentByWallet.ts) sends `walletAddress`, while the reviewed [chat route](https://github.com/Meriem-BM/x402ops/blob/1fed614f9c79e1932e5e8927e3e043a15ade5170/app/api/agent/route.ts) reads only `userMessage` and uses a constant conversation ID. Its [agent factory](https://github.com/Meriem-BM/x402ops/blob/1fed614f9c79e1932e5e8927e3e043a15ade5170/app/api/agent/create-agent.ts) caches one agent. This reviewed path does not establish the README's claimed per-wallet conversation isolation.
- The [policy-card editor](https://github.com/Meriem-BM/x402ops/blob/1fed614f9c79e1932e5e8927e3e043a15ade5170/components/agent-detail/policy-card.tsx) closes its dialog on Save; that handler does not persist the edited settings.
- The reviewed [CDP service](https://github.com/Meriem-BM/x402ops/blob/1fed614f9c79e1932e5e8927e3e043a15ade5170/services/cdp.ts) creates an `ethValue <= limit` signing criterion. This method alone does not implement an accumulated daily USDC budget or vendor allowlist, and its catch logs policy-application failures without rethrowing. This is a scoped source finding, not a claim about every deployed protection.

Initial recommendations from the review (the later user approval above expands presentation scope):

| Product idea | Countersign application | Timing |
|---|---|---|
| Clear agent identity and wallet status | Existing Controls: guarded/naive labels, public addresses, active state, gas balance/mode | Existing Phase 4 scope |
| Human-readable policy overview | Existing Controls: registered payouts, remaining PO budgets, daily cap and waiting changes | Existing Phase 4 scope |
| Explainable activity | Existing Inbox proposal/flags and Ledger Paid/Blocked receipts; distinguish AI refusal, contract block and execution error | Existing Phases 2–4 scope |

Nine wallet accounts do not mean nine AI agents: guarded and naive are the two planned agent identities; owners, deployer, attacker and vendors serve other roles. Their public accounts and test funds exist, but agent software, the vault and the live payment pipeline remain unbuilt. Countersign's proposed distinction is invoice-specific, contract-enforced controls plus public attack evidence, with the explicit caveat that fabricated invoices can still pay registered vendors within approved budgets. This distinction is a design goal until implementation and tests prove it.
