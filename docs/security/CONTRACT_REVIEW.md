This is a development review, not an independent audit. No live contract has been deployed, and Phase 1 is not complete.

- Normal Foundry suite: 90 tests passed; two additional local script-integration tests passed. Final combined run is recorded in `forge-tests.txt`.
- Four fuzz tests run 512 cases each. Six invariant campaigns (native/ERC-20 conservation, registered destinations, budget limits) run 128 sequences of depth 128 each; handlers exercise successful payments, policy blocks, unknown callers and time rolls. After-campaign checks prevent a vacuous no-payments run.

- Slither: 10 contracts, 102 detectors, 11 findings. No high findings; one medium, eight low and two informational triaged below. Reports are committed.
- Provided frontend baseline is commit `87135b1`; implementation timestamps reflect the human's explicit immediate-start override. No remote or GitHub repository was created.

## Slither triage

| Finding | Assessment |
|---|---|
| Medium: division before multiplication in period roll | Intentional integer rounding: advance the original start by complete periods, preserve the remainder, refill once. Native and token tests cover multiple skipped periods and compare the anchored start. Multiplying first would change the required policy. |
| Eight low timestamp findings | The product explicitly uses timestamp-based delay, expiry, UTC days and periods. Tests cover ETA minus one, exact ETA, exact expiry, next second, UTC reset and multi-period rollover. Validator timestamp latitude remains; 120 seconds is a demo delay, not a production monitoring guarantee. |
| Informational: execute complexity | Seven fixed, typed change kinds; no arbitrary call target/calldata. Each expansion is delayed and revalidates its applicable preconditions. Tests cover initial setup, duplicate changes, cancellation, re-execution and stale state. |
| Informational: native low-level call | Required native transfer; result checked. Shared nonReentrant guard on pay and execute; payment effects occur before the call, and failure rolls back state. Rejecting and reentrant payout fixtures pass. |

## Manual review and diagrams

- [Inheritance](inheritance.svg) generated by Slither. Ownable2Step overrides ownership transfer; Pausable and ReentrancyGuard have separate responsibilities.
- [Function authority](authorization.svg) checked against Slither's `function-summary.txt`.
- [State writes](state-writes.svg) checked against `vars-and-auth.txt`.
- No delegatecall, proxy, upgrade function, arbitrary external execution, signature verification, price oracle, AMM or lending interaction in the vault. Upgrade/price/flash-loan checks therefore do not apply to this vault after source inspection.
- Agent caller validation precedes rule checks. Twelve policy reasons have event-argument and no-transfer tests in both asset modes.
- OverBudget and OverDailyCap use subtraction guards, so hostile uint256-max amounts and lowering the cap below prior spending produce policy results without overflow/underflow reverts.
- Transfer errors roll back PO spend, daily spend and invoice-paid state. SafeERC20 tests include normal, false-returning, reverting and no-return tokens.
- Payouts reject zero and the vault itself. Success uses the registry value, never arbitrary proposal data. Withdrawals resolve the current owner when executed.
- Pending permission expansions are not automatically cancelled by pause/revoke/deactivate. The owner must cancel unwanted queued changes. This matches the explicit cancellation workflow.
- Inherited ownership renunciation can permanently remove administration; it is not exposed in the frontend. Owner compromise without a separate reviewer/canceller remains outside this demo's protection.
- Hashes are agent-supplied. Backend normalization excludes amount, but the contract cannot prove a hash came from a genuine invoice. Fresh fake invoice identities can spend approved vendor budgets. Replay protection is not forgery protection.
- Amounts, payout addresses and hashes are public. Invoice text stays off-chain. Hashes can reveal low-entropy invoice numbers by guessing; no privacy guarantee is made.
- Transaction ordering can consume a shared budget or cause a duplicate rejection. A queued payout change executed before a stale payment makes that payment fail its payout check; it cannot redirect that stale payment to another recipient.

## Token integration review

Public explorer source and its 12 imported source files were retrieved for both configured tokens:

- [Testnet token](https://scan.bohr.life/address/0x75edC9335175Fc0552D51D48439F229c10420fe3?tab=contract)
- [Mainnet token](https://scan.botchain.ai/address/0xaBabc7Ddc03e501d190C676BF3d92ef0e6e87a3C?tab=contract)

Both explorer records identify the same small USDT contract, compiler 0.8.22, `IsProxy: false`, inheriting OpenZeppelin ERC20, ERC20Burnable and AccessControl. Its only token overrides are constructor-set decimals and role-controlled mint. Imported transfer/update code credits the stated amount and returns true. These are BOT-issued contracts named USDT; the name alone is not evidence of Tether issuance, reserves or redemption.

| Pattern group | Result / boundary |
|---|---|
| Missing/false returns or transfer revert | SafeERC20 wrapper; dedicated rollback/compatibility tests. |
| Hooks, fees, rebasing, yield-bearing partial transfers | None found in the retrieved implementation/imports. Arbitrary such assets remain unsupported; the immutable token cannot be replaced in the vault. |
| Proxy/upgrades, injected code, multiple representations | Explorer marks both non-proxy; no upgrade path found in retrieved source. Verify selected chain/address before deployment; zero token address alone means native BOT. |
| Mint/burn/scarcity | MINTER_ROLE can increase supply; holders can burn and approved spenders can burnFrom. No supply cap or scarcity claim. Vault never grants approval, so it does not authorize third-party burns. Role holders and economic backing were not independently audited. |
| Pausing/blocklists/transfer restrictions | No pause, blacklist or fee switch found in the retrieved token code. Never infer Ethereum-USDT behavior from its ticker. |
| Metadata/decimals | Six decimals checked in Phase 0 and again in the real-token fork. Setup reads actual decimals, uses exact integer conversion, rejects excess precision. No amount scaling in contract payment logic. |
| Approval races, permit, transferFrom-self, approval zero quirks | Vault uses direct safeTransfer only: no approval, permit or transferFrom path. |
| Zero transfers/zero address/large amounts | pay logs ZeroAmount; registry rejects zero; budget checks bound amounts before transfer; normal ERC20 checked arithmetic remains. |
| ERC721 | No NFT integration. |

Mainnet source inspection is not a mainnet transfer test. Real deployment, funding, owner setup and Paid/Blocked explorer evidence remain pending the unavailable signing credentials/funding. Do not tag `phase-1-done` or describe a local fork as a live deployment.
